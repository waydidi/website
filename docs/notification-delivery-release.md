# Booking notification delivery

This changes existing booking confirmation email/PDF delivery and the general, assignment and chat Telegram outboxes. It does not introduce a marketing message, charge, refund or automatic resend of an uncertain result. The owner review workspace is implemented separately below; missing legacy-job reconciliation, production verification, storage migration and recovery remain in progress.

## Behaviour

The guarded booking confirmation and its channel jobs are one D1 batch, before external calls. A failed job insert rolls back that confirmation transition. Existing jobs retain their IDs. Null payment-intent input preserves the stored intent instead of replacing it with an older caller snapshot.

By default `BOOKING_BACKGROUND_DELIVERY=0` preserves inline first attempts. With `1`, only existing confirmation email/PDF jobs are deferred to `runDeliveryRecovery`, reached by the existing five-minute operations cron. Other existing trip/Telegram work still runs through its existing paths. Verify the deployed cron before enabling this flag; an unconfigured cron would leave these jobs queued.

Migration `0113_booking_delivery_payloads.sql` and first-use bootstrap add private message snapshots and blob parts. The envelope freezes the sender, recipients, subject, HTML/text, attachment and ride URL before the first possible provider request. It receives an opaque SHA-256 job key; retries use the same stored envelope. Large envelopes span 900-KiB D1 parts. Competing renderers cannot replace a winning snapshot. Reads verify contiguous parts, byte count and SHA-256 before sending. Message contents and tokens never enter application logs or the operations inbox.

A send records its start before network activity, with a 20-second HTTP timeout. HTTP 200/201 requires a usable provider message ID. `sent` means provider acknowledgment, not inbox delivery. Retryable failures use bounded exponential backoff and honor `Retry-After`. The first provider attempt starts a conservative 23-hour retry window, with at most 12 provider attempts; jobs older than seven days stop. The provider's documented idempotency retention is 24 hours: https://resend.com/changelog/idempotency-keys . This does not guarantee exactly-once email delivery.

Definite permanent rejection becomes `dead_letter`. Unknown outcomes remain sticky across later failed attempts and become `uncertain` when retry safety expires or the provider rejects the key. An interrupted attempt records an unknown outcome. Legacy attempted jobs without a recoverable original body also become `uncertain`; missing current credentials cannot erase that ambiguity. No automatic new-key resend is made. Owner/operations can see these jobs in the existing inbox without recipient details. Manual provider investigation and any deliberate new message remain separate from retrying the old job.

Claim timestamps fence final job and receipt writes. A worker whose lease was replaced cannot overwrite the current result. Expired rendering leases cannot start a provider request. Stored bodies are removed after seven days for sent jobs and 30 days for terminal review jobs; operational hashes/receipts remain. Recovery performs bounded cleanup even when the background flag is off.

## General Telegram outbox

The general `telegram_delivery_jobs` queue stops after 12 claimed attempts or seven days. Definite API rejections may retry within that budget; transport errors, malformed successes, changed private photo bytes and ambiguous provider responses require review. A send acknowledgment needs a positive integer message ID. Rate-limit delays from `parameters.retry_after` are persisted and cannot be erased by enqueueing the same job again. The existing JSON client can wait once for a short rate limit, and a definite quote rejection can remove the quote before one fallback; the limit counts job attempts rather than claiming a precise number of HTTP calls. Telegram does not receive an email-provider idempotency key. See the official response and rate-limit contract: https://core.telegram.org/bots/api#making-requests and https://core.telegram.org/bots/api#responseparameters .

Producers can update an unattempted queued payload. Once attempted, retries preserve it. Photo SHA-256 values are saved before the first provider request; a changed file stops for review instead of sending different evidence. Recipient/journey authorization is checked again after private-file reads. The worker must still own a sufficiently fresh lease immediately before sending. Final job and linked card/prompt/context writes are guarded by the same claim timestamp and acknowledged message ID, so a late response cannot update another attempt's state. A failed local commit after a provider acknowledgment records an uncertain result and retains a known message ID where possible.

Telegram client errors now contain fixed descriptions rather than arbitrary provider text, including for multipart uploads. Responses with a non-Boolean success field are rejected. The support settings list shows when automatic retries have stopped. General Telegram booking failures and terminal review jobs also appear in Operations without message bodies or destinations; unscoped chat jobs remain in Telegram settings. The owner review workspace preserves original retry budgets. A deliberate replacement message is a separate business operation; the review path cannot rekey or rebuild an exhausted message.

The general outbox reuses existing tables and runtime bootstrap; that slice adds no schema migration or new message category. The separate assignment/chat consumers now use the stored-message implementation below.

## Assignment and chat outboxes

Assignment and chat notifications keep their existing queue IDs, ownership checks and routing. They stop after 12 claimed attempts or seven days, persist rate holds, verify numeric message acknowledgments and fence result writes by the current claim. Missing credentials do not erase legacy ambiguity or bypass retry budgets. Already-attempted messages without a recoverable snapshot become `uncertain`; they are not silently rebuilt. A known blocked-bot diagnostic uses fixed allowlisted text, preserving useful operational information without retaining arbitrary provider descriptions.

Additive migration `0114_telegram_message_payloads.sql` and matching first-use bootstrap add private assignment/chat payload tables and a first-card claim table. Both consumers persist the rendered JSON envelope and SHA-256 before requesting Telegram. Retries reuse the original body, keyboard, reply target and destination. A changed assignment token/booking version, changed destination, invalid snapshot or changed chat assignee stops the old message for review. Assignment validity and fresh lease ownership are rechecked immediately before sending. The existing opt-in linked-driver message path remains in the general outbox.

An assigned chat's definite private-message rejection can fall back to the frozen group message. Rate limits and ambiguous outcomes do not trigger that fallback. Saved backoff applies to direct calls as well as cron recovery, and held jobs do not occupy every recovery slot. The attempt limit counts claimed attempts; the existing short flood wait and definite private-to-group fallback can each make more than one HTTP request within a claim.

Only one message may create a conversation's first group card. Other messages stay pending until that card is known, then use it as a reply target. An unknown first-card outcome keeps its claim for review rather than letting the next message create a duplicate. A blocked conversation is excluded from the recovery queue so unrelated conversations continue. Expired/closed chats stop; known skipped messages release an unused first-card claim. Incoming questions remain saved and visible in the web support inbox.

Provider acknowledgments, message status, root-card updates and routing mappings commit together under the current claim. A late response cannot mark a newer attempt sent or write its mappings. A database failure after acceptance leaves a processing/uncertain result for recovery and review, without a blind resend. Provider message IDs indicate acknowledgment rather than proof a staff member read the message.

Old private snapshots are cleared after seven days for sent notifications and 30 days for terminal review/skipped/cancelled notifications; hashes and known provider IDs remain. Chat snapshots and first-card claims cascade when their source messages/conversations are deleted. Cleanup also runs when the bot is disconnected. Operations includes uncertain/stopped booking notifications, and Telegram settings include stopped assignment/chat jobs and saved chat retry times.

Preserve these tables during rollback. Do not switch back to a consumer that rebuilds an attempted message or ignores terminal outcomes. Existing uncertain and ambiguous legacy jobs can be inspected in the owner review workspace, with explicit evidence required for each decision. These changes add no new message category and do not enable the optional background-email flag. Production account/configuration/cron checks remain pending.
